# Finance Dashboard
#### Video Demo: https://youtu.be/qpdqNwPuOLA
#### Description:

Finance Dashboard is a multipage web application, built with [Streamlit](https://streamlit.io), that lets a user create an account, log in, build a personal portfolio of stocks, and track how that portfolio is performing against live market data. Alongside the portfolio tracker, the app also shows recent price history for a small set of well-known companies and a cryptocurrency, and pulls in current business headlines through a news API. My goal was to combine several things I learned in CS50 — file handling, exception handling, classes, working with an external API, and persisting data to a database — into a single project I would actually want to use myself, since I already track a small personal portfolio by hand in a spreadsheet.

When the app starts, the user is shown a login form. If they don't yet have an account, they can switch to a registration form, choose a username and password, and the app stores their credentials in a local SQLite database (`finance.db`). Passwords are never stored in plain text: they are hashed with `bcrypt` before being written to the `users` table, and checked with `bcrypt.checkpw` on login, so even I, looking directly at the database, cannot read anyone's password.

Once logged in, the user lands on a dashboard built around Streamlit's `option_menu` navigation. From there they can select which companies they hold shares in (from a fixed list defined in `name_ticker.json`, which maps all the companies that Yfinance provides), enter how many shares of each they own, and submit the form. The app then calls the [`yfinance`](https://pypi.org/project/yfinance/) library to fetch the current price for each ticker, computes a running **average purchase price** per asset (a simple weighted average based on the previous amount/price and the newly added shares), and stores the result in an `assets` table in `finance.db`, keyed to the logged-in user's ID. On future visits, the dashboard reloads the user's holdings, refetches current prices, and displays a table comparing each asset's average price to its current price, plus a small explainer section on how to read "in profit," "breakeven," and "unrealized loss" states.

A second part of the dashboard renders historical price charts of large-cap companies (Tesla, Apple, Microsoft, Google, Amazon, Meta) and Bitcoin (I tried to put more cryptocurrencies on the view, but BitCoin it is way more valuabe than the others, so would smash the others lines to bellow, being unreadble to anyone), using `yfinance` to pull one month of daily closing prices and `altair` to draw an interactive line chart with a hover tooltip, and all this chart features are weel described in ['streamlit documentation'](https://docs.streamlit.io/develop/tutorials/elements/annotate-an-altair-chart) . The third section is a simple news feed: it calls NewsAPI's top business headlines endpoint and renders each article's title, description, and image (falling back to a local placeholder image if the article has no image or the image URL doesn't resolve).

**File overview**

- `project.py` — the entry point. Contains `main()`, which manages page routing through `st.session_state` flags (logged in / registering / logging in) and renders the login, registration, dashboard, charts, and news views. It also contains the project's required helper functions: `register` and `login` (account creation/authentication), `make_chart` (renders an Altair price chart), `what_new` (fetches news headlines), `yf_companies_names` (reads the ticker map), `get_user_id`, `get_user_assets`, `store_companies`, and `users_assets_check` (all database reads/writes for a user's portfolio), and three small, pure data-shaping functions — `make_user_dict`, `dict_to_df`, and `get_tickers_for_dash` — that turn raw database rows into the dictionaries/DataFrames Streamlit displays. It also defines two classes, `Finance_data` (fetches and reshapes historical price data for the charts) and `User_companies` (fetches current prices for a user's chosen tickers and formats them for storage).
- `test_project.py` — pytest tests for three of the pure helper functions above (`dict_to_df`, `get_tickers_for_dash`, `make_user_dict`). I deliberately tested these three rather than the database- or network-facing functions, since they take plain Python data in and return plain Python data out, so they can be verified without touching SQLite or the internet, wich I was not able to check it for skills issues.
- `requirements.txt` — the external packages the project depends on (`streamlit`, `streamlit-option-menu`, `yfinance`, `altair`, `pandas`, `requests`, `bcrypt`), so anyone can recreate my environment with `pip install -r requirements.txt`.
- `name_ticker.json` — a small JSON file mapping the company names shown in the "select your assets" dropdown to their real stock tickers, so the UI can show readable names while the backend works with the symbols `yfinance` expects.
- `finance.db` — the SQLite database created on first run. It has two tables: `users` (`user_id`, `user_name`, `user_password`) and `assets` (`asset_id`,`user_id`, `asset_ticker`, `asset_price`, `asset_amount`, `average_price`, `asset_date`, `created_at`).
- `login.py`, `register.py`, `dashboard.py` — empty placeholder files. Streamlit's `st.Page()`/`st.navigation()` API requires a file to point to in order to register and label a page in the app's navigation, but all of the actual login, registration, and dashboard logic is implemented directly in `project.py`, driven by `st.session_state` flags. These three files exist purely so Streamlit has something to reference for the navigation UI.

**Design decisions worth mentioning:** I chose to store only the *current* average price and share count per asset, rather than a full history of every purchase, to keep the schema simple — the trade-off is that I can update a position but can't show a user their full buy history, which would be a natural next feature. I used classes for `Finance_data` and `User_companies` specifically because each one bundles related state (tickers, a time period, fetched data) with the operations that act on it, which made the multi-step "fetch → process → store" flow easier to follow than passing the same variables between several standalone functions. Error handling throughout favors returning a message or `None` rather than letting Streamlit crash mid-render, since a bad API response or missing ticker shouldn't take down the whole dashboard for the user.
